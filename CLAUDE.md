# ccscraper — notes for working in this codebase

Self-hosted scraper service with a staged fallback pipeline (curl_cffi → crawl4ai → Camoufox → SeleniumBase CDP Mode → Firecrawl), producing Markdown by default (raw HTML / LLM-text on request) over an authenticated async-job HTTP API. The workload is bot-protected OEM product catalogues (Dell, Lenovo, HP, Acer), so every stage impersonates a real browser. See `README.md` for the product-level overview; this file is about working in the code.

## Architecture at a glance

- `app/` (FastAPI) only creates/reads job records and enqueues arq jobs — including `app/mcp_server/`, the MCP endpoint mounted at `/mcp`, which submits the *same* `run_scrape_job` and polls the same `job:{id}` key rather than fetching in-process — it must never import `pipeline.stages`, `camoufox`, `playwright`, `seleniumbase`, `curl_cffi`, `crawl4ai`, or `firecrawl`. This keeps `docker/api.Dockerfile` free of the three browser runtimes `docker/worker.Dockerfile` carries.
- `worker/` (arq) owns all actual fetching. `worker/main.py` builds long-lived resources once at startup (one `curl_cffi.AsyncSession` shared by Stage 1 and the robots gate, `BrowserSlots`, `RobotsGate`, `DomainMemory`, `ScrapeCache`, and an `AsyncFirecrawl` client that is `None` when no key is set) and stores them on `ctx`; `worker/tasks.py` builds the per-job stage list from `ctx` and calls `pipeline.orchestrator.run_pipeline`.
- `pipeline/orchestrator.py` is the only place that decides stage escalation order. It consults `pipeline/domain_memory.py` to try the last stage known to work for a domain first — then falls back to the stages that shortcut skipped, and forgets the entry if everything fails — and treats `UnsupportedContentType` (raised via `pipeline/stages/content_type.py` by every stage that can see a Content-Type) as immediately terminal — never escalate a PDF/image to a browser, a browser can't turn it into HTML either.
- `extract/` is deliberately decoupled from which stage won. `extract/models.py` has zero heavy dependencies (safe for the `api` container to import, for response typing only); `extract/converter.py` and the `markdown.py`/`llm_text.py` wrappers over it pull in crawl4ai and are worker-only.

## Load-bearing facts, verified against source and live probes — don't re-guess these

- **Stage 1 exists because a plain HTTP client cannot fetch two of the four target vendors at all.** Probed 2026-08-29: `hp.com` and `acer.com` return `HTTP/2 INTERNAL_ERROR` (or hang on HTTP/1.1 delivering zero bytes) to httpx/curl regardless of `User-Agent`, and a normal 200 to the identical request through `curl_cffi` with `impersonate`. This is a TLS/JA3 + HTTP2 fingerprint check, not a header check. Never "simplify" Stage 1 back to httpx.
- **Never pass a `User-Agent` into any stage.** `settings.user_agent` is consumed *only* by `RobotsGate` for robots.txt directive matching. curl_cffi's `impersonate=` installs a full header set in the real browser's order, and Camoufox generates a UA coherent with its spoofed screen/WebGL/font fingerprint — overriding either desynchronises the headers from the fingerprint, which is itself a detection signal.
- **`pipeline/quality.py` must match markers and count text against `clean_html()` output, never raw HTML.** Two separate real bugs came from scanning raw HTML, both caught by live testing:
  - Text counting: a SPA embedding content as JSON in an inline `<script>` (quotes.toscrape.com/js/) looks content-rich when it is an empty shell.
  - Marker matching: lenovo.com product pages inline `RECAPTCHA:"https://www.recaptcha.net/..."` as a JS config path. Matching `_CHALLENGE_MARKERS` against raw HTML saw "captcha" and rejected a clean 200 fetch as a bot challenge — escalating **every** Lenovo product page to a browser, 13.8s instead of 0.2s.
- **There is no visible-text-to-HTML ratio check, and adding one back will break the target workload.** It was removed after measurement: against the raw denominator it failed 4 of 7 real vendor pages (lenovo laptops 0.0030, hp shop 0.0052) while quotes.toscrape.com/js/ — an actually-empty shell — scored 0.0165, *higher* than three of them; against a cleaned denominator the shells scored higher still (0.0753). The metric tracks how much JavaScript a page ships, not whether it has content, and modern e-commerce ships a lot of both. `_MIN_TEXT_LENGTH` is what actually catches shells.
- **reddit.com's block is a 200, not a 403, and it is caught only by a challenge marker.** Probed 2026-08-29: `www.reddit.com` answers Stage 1 with a "Prove your humanity" interstitial at HTTP 200 carrying ~270 chars of visible text inside 167KB of inline CSS/SVG — above `_MIN_TEXT_LENGTH`, just under `_UNRENDERED_MIN_HTML_LENGTH`, and matching none of the Cloudflare markers. Before `"prove your humanity"` was added to `_CHALLENGE_MARKERS`, Stage 1 "succeeded" on that page and the pipeline never escalated. Stage 2 gets the real content in ~4s, Stage 3 in ~12s. (Reddit's *other* interstitial, an 8KB JS proof-of-work that auto-submits a `solution` form, is already caught by `text_too_short`.) Reddit's robots.txt is `Disallow: /` for every user-agent, so any Reddit job needs `"robotstxt": false`.
- **`pipeline/browser/settle.py` must gate its early return on `is_settled`, not on size stability alone.** A bot-challenge interstitial is a *static document by construction*: store.acer.com's Akamai sensor page holds a byte-identical 2,615-byte body for ~4.5s while its JavaScript runs, then replaces it with the real 595KB / ~17.7k-character page at about t+9s. Two stable polls is 1.0s, so a pure size check returns the 32-character challenge and every stage reports `text_too_short` on a page that renders fine. Stages 3 and 4 pass `pipeline/quality.py`'s own `is_good_enough` as the predicate — there must stay exactly one definition of "good enough" in the pipeline, and the settle budget stays the hard cap so a page that never passes just costs the budget instead of hanging.
- **A remembered stage must never become a dead end.** `pipeline/orchestrator.py` tries the domain-memory stage first, then the stages that shortcut skipped, and calls `DomainMemory.forget()` when every one fails. One lucky SeleniumBase win pinned store.acer.com to that stage for the full 7-day TTL, so Camoufox — the stage that could actually fetch it — never ran again and the entry never expired on its own.
- **Stage 2 must pass crawl4ai an explicit `user_agent`, and it is the one exception to "never pass a User-Agent into a stage".** Both obvious choices are wrong, measured 2026-09-02 against `httpbin.org/headers`. crawl4ai's default is a hardcoded, *malformed* `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 Chrome/116.0.0.0 Safari/537.36` — the `(KHTML, like Gecko)` token is missing — from an engine that is Chrome 148, and it derives a matching `Sec-Ch-Ua: v="116"` from it. Passing `user_agent=""` to get Playwright's own is *worse*: the header then reads `HeadlessChrome/148` with `Sec-Ch-Ua: "HeadlessChrome"`, while crawl4ai's stealth patch separately rewrites `navigator.userAgent` to `Chrome/148` — so the page and the request disagree. reddit.com reads the header and acts on it: 3/3 trials returned ~850KB of real content for a non-Headless UA and a 190KB shell for the HeadlessChrome one. `_coherent_user_agent()` probes the engine's own string once per process and drops the `Headless` token, so header, client hints and `navigator.userAgent` all agree. `user_agent=None` is not an option — it crashes crawl4ai's own client-hints generator.
- **Stage 2's `wait_until` is `"load"`, and both alternatives were measured.** 3 trials per cell, 2026-09-02, scored against `is_good_enough`: `domcontentloaded` returns before reddit hydrates (1/3, 3.4s); `networkidle` never fires on lenovo.com, which polls forever (0/3, timing out at 45.6s); `load` passed 3/3 on reddit, lenovo and hp and was fastest overall (4.4s / 6.9s / 6.4s).
- **Stage 2 does not settle-poll, on purpose.** `settle_until_stable` needs a repeatable `async () -> str` and crawl4ai's `arun()` is one-shot. A page still running a challenge script fails `is_good_enough` and escalates to Stage 3, which does settle. Do not "fix" this with `delay_before_return_html` — `pipeline/browser/settle.py` records why a fixed sleep is a coin flip on these sites.
- **crawl4ai's stealth is JS-injected and visibly so, which is why Stage 3 still exists.** bot.sannysoft.com dumps the *source* of the overridden getters: instead of `function get userAgent() { [native code] }` it renders crawl4ai's `current_ua.replace("HeadlessChrome/", "Chrome/")` as page text. Stage 2 is therefore excluded from the sannysoft/browserscan probes in `tests/integration/test_antibot_live.py` — asserting it passes them would be asserting something untrue. It is a cheap real browser for the majority of pages, not a fingerprint-proof one.
- **Neither crawl4ai converter call raises; both return their error message as content.** `LXMLWebScrapingStrategy.scrap()` swallows any lxml error and hands back a `cleaned_html` that is literally a `<div id="crawl4ai_error_message">Crawl4AI Error: ...</div>` with `success=False`, and `DefaultMarkdownGenerator.generate_markdown()` returns `"Error converting HTML to markdown: ..."` as `raw_markdown`. Unchecked, either is served to the caller *as the page*. `extract/converter.py` checks `.success` and screens the known error prefixes, and returns `""` for every failure so callers have one sentinel.
- **`extract/llm_text.py`'s `_MIN_KEPT_RATIO` guard survived the trafilatura→crawl4ai swap because the failure is a property of boilerplate pruners in general.** `PruningContentFilter` can misjudge a product page the same way, and has an extra route to it: it decomposes `<form>`, `<header>`, `<aside>`, `<nav>`, `<footer>` and `<iframe>` outright before any scoring runs, and on a configurable PDP the specs and price live inside the `<form>`. No threshold tuning reaches that — only the fallback does. The ratio is measured against `fit_html` (the HTML the pruner kept), **not** against `fit_markdown`: Markdown carries inline `[text](url)` links and is longer than the visible text it came from, so a ratio taken on it is biased upward and the guard fires less often than it should.
- **`extract/structured.py` must keep receiving raw `html`, never `cleaned_html`.** crawl4ai's scraper removes every `<script>` from the tree before serialising, and `PruningContentFilter` removes them again, so no ld+json survives into either text format. Feeding the cleaned HTML to `extract_products()` returns `[]` on every page and the product table silently vanishes.
- **`import crawl4ai` does an `os.makedirs` at module scope** (its `async_database`, under `CRAWL4_AI_BASE_DIRECTORY` or `$HOME`) and raises `OSError` if that is unwritable. Because `extract/converter.py` imports it, that is now a startup requirement of the *extract layer*, not just of Stage 2 — hence `ENV CRAWL4_AI_BASE_DIRECTORY` in `docker/worker.Dockerfile`. It must be in the process environment before Python starts; `.env` is too late, and `AsyncWebCrawler.__init__` binds its own default at function-definition time. Note the spelling: `CRAWL4_AI_*`, not `CRAWL4AI_*`.
- **`build_from_html` runs on a worker thread (`asyncio.to_thread`), not the event loop.** The conversion parses the whole document twice — lxml for the cleaned HTML, BeautifulSoup inside the pruner — synchronously, and a catalogue page is megabytes. Inline it stalls every other job on the worker, and it runs even when Stage 1 won in 0.2s.
- **Do not run `crawl4ai-setup` in the Dockerfile.** It downloads a *second* `--force` Chromium through patchright that nothing on the default `PlaywrightAdapter` path ever launches, and re-downloads on every rebuild. `python -m playwright install --with-deps chromium` is sufficient. That command runs its own `apt-get update`, so the lists have to be cleaned again in the same layer; and its `--with-deps` set does not cover the hand-listed libs Camoufox's Firefox needs (`libgtk-3-0`, `libxcursor1`, `libxi6`, `libxrender1`, `libxtst6`, `libdbus-glib-1-2`, `libxss1`, …) or the apt `chromium` package Stage 4 finds on PATH — don't prune them.
- **Challenge-marker matching only applies below `_MARKER_CHECK_MAX_TEXT_LEN` characters of visible text.** A long-form article that mentions "captcha" (e.g. an article *about* web scraping) must not be flagged for using the word — only short, boilerplate-heavy pages get marker-checked.
- **SeleniumBase's sync helpers must never be imported in the worker.** `sb_cdp.Chrome` / `SB()` apply `nest_asyncio` to the running loop, which inside arq would patch the worker's own event loop. Stage 4 uses only the async `cdp_driver.start_async()` surface. (`firecrawl-py` *declares* `nest-asyncio` as a dependency but never imports it — inert, but do not be the one who applies it.)
- **Stage 4 reconstructs its HTTP status from CDP.** `page.get_content()` returns HTML with no status, and `quality.py` needs one for `{401,403,429,503}`. `_DocumentResponses` subscribes to `network.ResponseReceived`, keeps top-level `DOCUMENT` responses, and reconciles against the final URL, falling back to `200`. The handler must be attached to a blank tab *before* navigating, or the main-frame response is missed.
- **All three browser stages launch per job rather than pooling.** Camoufox fixes its fingerprint at launch, so a shared browser would present one identical device for every request to a host — the correlation signal the stage exists to defeat. `BrowserSlots` only bounds concurrency; it holds no browser.
- **The Firefox and CDP-Chromium stages want opposite display settings, which is why there are separate knobs (`stage3_use_xvfb`, `stage4_use_xvfb`) and not one.** "Real headless is trivially detectable" is true of *Chromium* and is why Stage 3 keeps `xvfb=True` (Linux-only, so local macOS/Windows dev falls back to headless and is the weaker configuration). It is **false for Camoufox**, and running it under Xvfb is an active liability: measured in the worker container 2026-08-29 over 3 interleaved trials each, store.acer.com's Akamai challenge never cleared under Xvfb (32 chars after 23s, 3/3) and cleared in ~5.5s headless (3/3). The fingerprint shows why — under Xvfb Camoufox's WebGL spoof advertises `ANGLE (NVIDIA, NVIDIA GeForce GTX 980 …)` while the container software-renders it, and a GPU claiming a GTX 980 that draws like llvmpipe is a contradiction; headless exposes no WebGL at all, so there is nothing to contradict. Neither mode is flagged by bot.sannysoft.com or browserscan.net, so this costs no stealth. Stage 3 was 403 either way, so its setting is unchanged for lack of evidence, not because it helped.
- **The MCP endpoint is mounted, not routed, and that changes three things.** `app/mcp_server/server.py` builds the server; `app/main.py` mounts it. (a) A mounted sub-application's own lifespan never runs, so `lifespan` in `app/main.py` must enter `app.state.mcp.session_manager.run()` itself — without it the first request to `/mcp` dies with `RuntimeError: Task group is not initialized`. `session_manager` only exists after `streamable_http_app()` has been called, which is why the server is built and mounted in `create_app()` and only touched in the lifespan. (b) FastAPI's `Depends(require_bearer_token)` never runs for a mount, so `BearerTokenMiddleware` in `app/auth/bearer.py` does the same static-token check at the ASGI layer. (c) Without `transport_security`, the SDK arms DNS-rebinding protection with a localhost-only allowlist and answers **421 Misdirected Request** to everything a reverse proxy forwards, logging the reason server-side only — `settings.mcp_allowed_hosts` empty means `enable_dns_rebinding_protection=False`, which is the correct setting behind Caddy.
- **The MCP app is mounted at `"/"` with the transport's default `/mcp` path, not at `"/mcp"` with `streamable_http_path="/"`.** The latter reads better and does not work: Starlette hands the sub-router an empty remainder, which it 307-redirects to `/mcp/`. Verified — every `POST /mcp` answered 307. The routers are included before the mount so they still match first; the only side effect is that unknown paths answer 401 instead of 404.
- **`scrape` defaults to `formats=["llm_text"]`; the REST API defaults to `["markdown"]`.** A tool result goes straight into a model's context and `raw_html` is routinely megabytes. Terminal failure statuses are returned as *data*, not raised as `ToolError` — the model has to tell `robots_disallowed` from `blocked` to pick a next move, and an error string flattens that. `ToolError` is reserved for an unknown `job_id`.
- **The response cache (`app/jobs/cache.py`) caches only `success`.** A `blocked`/`timeout`/`error` is usually transient; storing one for the 30-day TTL would take that URL out of service for a month. It lives in `app/`, not next to `domain_memory.py` in `pipeline/`, because `docker/api.Dockerfile` copies only `app/`, `common/` and `extract/models.py` — and both tiers need it: the API/MCP tier reads through it, the worker writes it. Three further things about it that are not free to change:
  - **Each entry is two Redis keys**, `scrape_cache:meta:{key}` and `scrape_cache:body:{key}`, written with the same TTL. `GET /cache` lists metadata only; a single-key design would make listing 500 entries a multi-gigabyte response, since `raw_html` is routinely megabytes.
  - **`clear()` is a prefix-scoped `SCAN` + `DEL`, never `FLUSHDB`.** arq's queue, `job:`, `robots:` and `domain_memory:` all live in the same database — a `FLUSHDB` would destroy every in-flight job. It collects keys before deleting so the cursor walks an unmodified keyspace.
  - **No cache key travels through arq.** `cache_key(url, formats, robotstxt)` is pure and both tiers recompute it, so `enqueue_job("run_scrape_job", id, url, formats, robotstxt)` is unchanged. `refresh=True` suppresses only the *read*: pre-deleting the entry would throw away a usable result if the refetch then fails.
- **The robots.txt gate fetches with curl_cffi, not httpx, and that is load-bearing.** "robots.txt is a small well-known text file, so fetching it is not what gets fingerprinted" is the assumption this code used to carry, and it is false: the block is at the TLS/HTTP2 handshake, before the path is ever sent. Measured 2026-08-29, httpx read-times-out on `store.acer.com/robots.txt` *and* `www.acer.com/robots.txt` under every `User-Agent` (`www.hp.com` answers it fine, which is what made this look host-specific), while curl_cffi gets a normal 200 in <0.2s. Because an unreachable robots.txt fails closed, plain httpx turned an allow-all robots.txt into a permanent `robots_disallowed` for every acer host — and `RobotsCache.set` only runs on success, so every job re-paid the hang. Don't send a `User-Agent` header with it either; `impersonate` installs a coherent one, and `settings.user_agent` is for matching directives, not for announcing an identity the TLS fingerprint contradicts.
- robots.txt fetch failures (timeout/5xx) fail **closed** — treated as disallowed — rather than open, per the "respect robots.txt" requirement (`pipeline/robots/gate.py`). A 404 means allow-all (spec default); that's a different case from a fetch error and must stay that way.
- The robots.txt gate is bypassable per-request via `"robotstxt": false` in the `POST /jobs` body (`JobCreateRequest.robotstxt` → `Job.robotstxt` → arq job arg → `run_pipeline(..., respect_robots=...)`). Default is `true` (respect it) at every layer, so omitting the field changes nothing. A bypass must skip the check entirely, not fetch-and-ignore — `RobotsGate.check()` should never be called when it's off (see `test_orchestrator_robots_bypass.py`).
- `extract/structured.py` parses ld+json with `strict=False` — real sites (lenovo.com) ship raw control characters inside string values, which strict `json.loads` rejects, losing the whole block. It must never raise: a malformed block on one page cannot fail a job.

## Testing

- `tests/unit/` — fast, no real network/browser: `respx` for HTTP mocking, small fake-Redis doubles for cache/store classes (see `FakeCache`/`FakeRedis` patterns already in the test files — reuse that shape rather than adding a new mocking library). **`respx` patches httpx's transport and cannot intercept curl_cffi**, which drives libcurl directly — `test_stage1_content_type.py` and `test_robots_gate.py` run a real loopback `http.server` instead. httpx *is* now a worker runtime dependency (firecrawl-py pulls it in), but no code path of ours uses it to fetch a target — it only talks to `api.firecrawl.dev`, which does not fingerprint us.
- `tests/unit/test_mcp_server.py` drives the tools through the SDK's **in-memory** `Client(mcp)`, which connects straight to the server object and skips HTTP — so it cannot see the bearer middleware at all. That is why `tests/unit/test_mcp_auth.py` exists separately, at the ASGI layer via `httpx.ASGITransport`.
- The REST routes are covered via the `api` fixture in `tests/unit/conftest.py`, which builds the real app and assigns fakes to `app.state`. `httpx.ASGITransport` deliberately does **not** run the lifespan — which is what would otherwise open a real Redis connection and arq pool. Two consequences: `app/main.py` builds an app at import time, so the fixture imports it only after `AUTH_TOKEN` is in the environment and calls `get_settings.cache_clear()`; and httpx merges client-level headers into per-request ones, so an auth test needs its own client rather than `headers={}`.
- `tests/unit/fakes.py` holds the `FakeRedis`/`FakeArqPool` doubles for the `app/` tier — the response cache needs `mget`/`delete`/`scan`/`pipeline` and recorded `ex=` values, which the two-method fakes in the pipeline tests don't have. Its `scan` takes a `scan_batch_size` so cursor-resume paths are actually exercised rather than always returning everything at once.
- `tests/integration/test_consent_dismiss.py` — runs a real headless **Firefox** via the `playwright_page` fixture in `tests/conftest.py`. Firefox, not Chromium: `pipeline/consent/dismiss.py`'s only production caller is Stage 2, and Camoufox is a patched Firefox, so the test runs on the engine the code actually runs on. That fixture exists on purpose instead of using `pytest-playwright`'s built-ins, which are sync-API only and would clash with this codebase's async-only Playwright usage. Fixtures simulating a CMP banner must include the actual removal JS a real CMP script would run (an `onclick` handler) — a static fixture with no script only proves a button got clicked, not that dismissal worked.
- `tests/integration/test_antibot_live.py` — marked `live` and deselected by default via `addopts = "-m 'not live'"`. It is the only test that verifies the premise the pipeline exists for (that the stages are not detected), so run `pytest -m live` before trusting any change to a stage. Asserting absence of markers must be done against `clean_html()` output: bot.sannysoft.com's own detector source contains `if (/HeadlessChrome/.test(...))`, so a raw-HTML scan reports a detection on a page that passed.
- Run everything: `.venv/bin/python -m pytest -q` — needs `python -m camoufox fetch` and `playwright install firefox` done once first.
- When testing the API/worker live (not just pytest), a sandboxed/CI shell's Docker daemon may be unreachable — fall back to running `uvicorn app.main:app` and `arq worker.main.WorkerSettings` directly against a local Redis (see README's Development section) rather than assuming `docker compose up` works everywhere.

## Conventions

- Async throughout — no sync browser/httpx/redis clients anywhere in `app/`, `worker/`, or `pipeline/`. This is what rules out SeleniumBase's sync API (see above).
- No speculative abstraction: stages, error types, and config fields exist because something in the pipeline actually uses them today. If you add a new field or exception, wire it to real behavior in the same change rather than adding it "for later."
- Comments are rare and explain WHY (a non-obvious constraint, or a bug this code specifically avoids repeating) — never WHAT the code does.
